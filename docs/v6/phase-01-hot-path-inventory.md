# Phase 1.7R baseline whole-collection inventory

Read-only source audit on 2026-09-08 before the remediation was implemented. This is an input to `phase-01-architecture-remediation.md`, not a PASS declaration. Line numbers below identify the entry implementation and may move during remediation. No operator data, live provider, database, or remote resource was read by this audit.

`HOT_PATH` means an ordinary request, ingestion, publication, scheduler, or worker operation. A scan is still a scan if its returned array is sliced afterwards. `ADMIN_PATH` does not by itself justify an unbounded scan: an explicitly bounded admin tool or an unsupported Cloudflare capability is required. Whole-file internals may remain in the legacy adapter; the shared domain caller must have an indexed-compatible operation.

## Identity constraints that must survive indexed storage

Three established entrypoints deliberately have different identities. A single storage identity index may use namespaced aliases for them, but it must not silently replace their domain predicates.

1. `createProduct` uses `duplicateKeys`: sourceItemId, then sourceId, then externalId with trimmed lowercase ID; broad canonical URL normalization forces HTTPS and strips www/tracking; affiliate URL also participates. Exact normalized merchant/title is a fallback only when that product has no stable source/URL key. A shared merchant and merely similar title is not enough.
2. `upsertSourceCandidateProduct` validates sourceId/externalId, source, and title. Identity is exact `(source, sourceId)` matching product sourceId/externalId or existing sourceMappings; canonical identity is conservative `normalizeProductIdentityUrl(originalUrl)` across products and mappings. It preserves HTTP versus HTTPS and host prefixes, removes hash/UTM and selected click IDs, sorts query parameters and trims trailing path slashes. Affiliate URLs and titles never identify source candidates. An original URL equal to the affiliate URL is excluded. Indexed source and URL results must be unioned by product ID, with two different matches rejected before writing.
3. `upsertCanonicalProduct` uses source/sourceId/externalId or exact raw original URL or exact affiliate URL, and returns unchanged when sourceHash matches. Source changes stale an existing review. This compatibility path cannot be silently redirected to a stricter/different source-candidate dedupe predicate.

Source-candidate merge preserves existing canonical ID; provenance, manual and verified evidence remain stronger than unverified incoming values. Missing fields and stronger qualifying evidence may enrich the aggregate. Source mappings retain firstSeenAt, update lastSeenAt, accumulate evidence, and do not overwrite prior mapped URLs/merchant data. Bounded retries may reread and rebuild a pure domain candidate, but must not repeat downstream side effects. Concurrent creators must encounter storage uniqueness/CAS conflict and retry against the committed mapping.

## Publication and revision constraints

`publishCanonicalProductTransaction` requires a durable claimed SAFE_PUBLISH/AUTO_SAFE_PUBLISH job, safe/free-only/launch settings, control mode, kill/pause state, actor/target/idempotency identity and existing approval or autonomous policy. Autonomous lifecycle remains PUBLISHING until the worker finalizes PUBLISHED. A caller's approval boolean is not authorization.

The entry implementation checks `updatedAt` before replacing the product and conditionally restores the old aggregate only if its own effect key and timestamp still identify the current write. The new common revision contract should strengthen this: read entity plus revision; apply with expected revision; return APPLIED/CONFLICT/NOT_FOUND; reject stale write without modifying the newer aggregate; rollback only the revision produced by that successful apply. Slug uniqueness must be checked by indexed lookup and enforced at commit for races. Publication effect/audit retries must remain idempotent.

`runGuardedOperation` is explicitly process-local idempotency. It is not the storage `StorageCommitGuard` authority primitive. Preserve its behavior while making durable CAS independent of the process-local registry. FileStorage may retain its existing lock/transaction implementation internally. Mongo currently persists revision/order envelopes and a collection metadata revision; any per-entity optimization must preserve coherence with those existing collection operations rather than writing an incompatible second Mongo product store.

All competing product writers matter: lifecycleStore, evidence repair, normal save, both upserts, create, and deliberate migration. A new integer revision on only one of those paths does not provide safe concurrency with the others. Tests should inject a competing lifecycle/product change and prove a stale expected revision cannot overwrite it.

## Price constraints

Existing configuration: 730-day retention, 730 snapshots per product, 20,000 collection records, forced unchanged checkpoint no sooner than 24 hours. Adjacent unchanged sourceHash is suppressed. A later return to a previous price is legitimate, so global uniqueness on `(product, price)` would lose history. The write contract needs latest-snapshot comparison, replay identity where introduced, and atomic insert-if-still-latest; read contract needs product predicate, stable time/ID ordering, bounded LIMIT and cursor. Global destructive retention/compaction is not part of local D1 Phase 2.

No test file was edited by this inventory audit.

## Reporting boundary

The eventual zero-VPS storage proof can establish FULL_SCAN=0 for the supported product/source/offer/publication-state/price/settings domain scenarios with a throwing FileStorage/full-collection spy. That alone does not establish the public catalog, discovery scheduler, lifecycle journal, source health, analytics, or full legacy worker as Cloudflare-ready. Unsupported domain capabilities must fail explicitly and must never use FileStorage in Cloudflare mode. Final reports should name remaining legacy scans and the exact supported D1 scope.
